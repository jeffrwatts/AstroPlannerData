# `comp_stars/<objectId>.json` Spec — Comparison Star Cache

## Purpose

`mobile/comp_stars/<objectId>.json` is a per-variable-star cache of AAVSO
comparison-sequence stars, generated by `vs_catalog.ipynb` in
`AstroPlannerData` at catalog-build time (when there's internet), and
published via GitHub Pages alongside `dso.json`/`vs.json`. It exists so
that both a field-use notebook (`field_check.ipynb`) and the AstroPlanner
app can show/use AAVSO comparison stars for a variable star target
**without a live call to the AAVSO VSP API** at time of use.

Unlike `dso.json`/`vs.json`, this is **not a single combined feed** — there
is one JSON file per `vs.json` `objectId`, e.g.:

```
https://jeffrwatts.github.io/AstroPlannerData/mobile/comp_stars/cyaqr.json
https://jeffrwatts.github.io/AstroPlannerData/mobile/comp_stars/v5563sgr.json
```

A file only exists for a given `objectId` if that object is present in
`vs.json` and the notebook was re-run since it was added. If the app
requests an `objectId` with no corresponding file (404), that just means
the cache hasn't been generated yet for that target — not an error in the
data itself.

## Format

A JSON array of objects, one per comparison star in the AAVSO sequence for
that target. Every field name/type below is fixed; if the app deserializes
with `kotlinx.serialization`, use `ignoreUnknownKeys = true` as with
`vs.json`/`dso.json` so extra fields are safe to add later.

```json
[
  {
    "auid": "000-BCB-041",
    "ra": 18.04752777777778,
    "dec": -24.28247222222222,
    "label": "53",
    "mag": 5.34
  }
]
```

## Field reference

| Field | Type | Required | Notes |
|---|---|---|---|
| `auid` | string | yes | AAVSO Unique Identifier for the comparison star (e.g. `"000-BCB-041"`). Stable across AAVSO's own systems — useful as a natural key if the app wants to dedupe/cache these itself. |
| `ra` | number | yes | Right ascension in **decimal hours**, range `[0, 24)`. Matches `vs.json`'s RA convention (not decimal degrees) — multiply by 15 to get degrees if needed. |
| `dec` | number | yes | Declination in **decimal degrees**, signed, range `[-90, 90]`. |
| `label` | string | yes | AAVSO chart label, e.g. `"53"` means an apparent magnitude of 5.3 (`"122"` means 12.2). This is the label AAVSO printed on their finder charts — display it as-is next to the star, don't reformat it into a magnitude unless you also want to show the raw `mag` field separately. |
| `mag` | number \| null | no | A single representative magnitude, generally V-band if AAVSO published one for this star, otherwise whatever band was available. `null` if no magnitude value could be resolved. |

## Fetch window (why coverage might look "too generous")

Each file is generated from a single AAVSO VSP query centered on the
target's own catalog RA/Dec, requesting a **2.0° diagonal field of view**
at **maglimit 14.5**. This is deliberately generous — wider than any single
piece of amateur equipment's real field of view — so the cache comfortably
covers:
- The real imaging FOV (e.g. ~1.0°–1.1° diagonal for a typical C8 + ASI294MC setup).
- Framing drift, dithering, and slight pointing error between sessions.

This means a given cache file may contain comparison stars well outside
what any single frame actually captures — that's expected, not a bug. Any
consumer that needs "stars actually in this frame" (like `field_check.ipynb`)
is responsible for filtering by its own frame's WCS/footprint; the cache
itself makes no claim that every star in the file is in every frame.

## What the app might do with it (context only — not dictated)

This section is a suggestion for the app-side implementation session to
evaluate, not a requirement from the notebook side:

- Likely fetched **per-target, on demand** (e.g. when the user opens a
  variable star's detail screen), rather than bulk-synced up front like
  `dso.json`/`vs.json` — since it's one file per object and most users will
  only ever look at a handful of targets in a session.
- Could be cached locally after first fetch (keyed by `objectId`) so
  repeat views of the same target don't re-fetch.
- Comparison stars could be overlaid on the existing Field Of View
  starfield image (see `field_of_view_nasa_api_spec.md`) using the same
  RA/Dec → pixel projection logic already used there, converting `ra`
  hours → degrees first.

## Open question for the app-side session

Whether to bulk-download all `comp_stars/*.json` files up front (requires
knowing the full list of `objectId`s from `vs.json` first, then fetching
each) or fetch lazily per-target the first time its detail screen is
opened. Both are supported by how the files are published; this is purely
an app-side design/caching-strategy decision.
